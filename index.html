ICT Midterm Project

Project Report

Designing an ICT Solution for a Real-World Problem

Problem and Context

Students and staff receive messages about classes, accounts, payments and campus services. Some are fake messages designed to look like official university notices. They may ask for a password or include an unexpected link or attachment.

If someone is unsure what to do with a suspicious message, they might ignore it, delete it or send it to the wrong person. That can slow down the university’s response, particularly if other people have received the same message.

A central reporting service would give students and staff a clear place to report these incidents. It would also help the university’s IT or security team receive and review reports consistently. The service should work on common devices and make it clear what information to include.

Target Users

UniSafe is intended for university students and staff, who may have different levels of experience with digital services. For example, Aliya is a student who receives an unexpected email containing a link. She wants to report it without opening the link or having to find the right university contact herself.

Proposed ICT Solution

UniSafe is a proposed web service for reporting suspicious messages and other cyber incidents. Users choose an incident type, describe what happened and enter the date. They can also attach a screenshot or file. Before sending the report, they can review the information they have entered.

After a report is submitted successfully, the service provides a confirmation and a reference number. Users can use that number to check the report’s status or find basic safety advice.

UniSafe does not automatically decide whether a report describes a genuine threat. University IT or security staff review the reports and decide whether further action is needed.

System Components

The current prototype is a browser-based interface built with HTML, CSS and JavaScript. A complete version would also need a university application server, a database for report details, secure file storage and an interface for staff to review reports. The technologies for the production server and database have not yet been selected.

System Architecture Diagram

Student or staff member → UniSafe web form → HTTPS → University application server → Restricted report database and file storage → IT/security staff

Once the server has stored a report successfully, it returns a confirmation and reference number to the user.

Network and Data Flow

The user enters the incident type, description and date, then reviews the report. In the proposed system, the browser sends this information to the university server over HTTPS. The server validates the report and stores it before returning a reference number.

Authorized staff can then review the report and update its status. If the service is unavailable, UniSafe should tell the user that the report was not sent and provide an official helpdesk contact.

Cloud or Mobile Technology

UniSafe is designed as a responsive website that works on phones and computers, so users do not need to install an app. The university could host it on its own approved infrastructure or use a suitably protected cloud service.

Users need an internet connection to submit a report. The site should therefore explain how to contact the university if the service is unavailable.

Main User Scenario

Aliya receives an unexpected email asking her to sign in through a link. She leaves the link unopened and visits UniSafe. She selects “Suspicious email or message,” describes what happened, enters the date and attaches a screenshot. After reviewing the details, she submits the report and saves the reference number.

University staff review the report and follow up if necessary.

Interface Prototype

The prototype demonstrates five screens or states: the report form, a review screen, a confirmation screen, a connection-error message and a status lookup. It is a front-end demonstration only; it does not send reports to a real university server or upload file contents. The demo reference number and status are stored locally in the same browser.

Technology Justification

A website lets students and staff use devices they already have without installing an app. A central server and database could help the university collect reports in a consistent way.

A real version would need to validate information on the server, limit access to authorized staff and protect any uploaded attachments. File uploads would also need safeguards, such as restrictions on file types and sizes [3].

Limitations and Future Development

The prototype does not have a live backend, staff dashboard or working file uploads. Its confirmation and status lookup are demonstrations and are not connected to university services.

Future development could include university sign-in, a staff review dashboard, secure file scanning, status notifications and accessibility testing. Before deployment, the service would also need to follow the university’s privacy and incident-response procedures.
